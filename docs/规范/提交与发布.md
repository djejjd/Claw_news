# 提交与发布

## 日常提交

提交信息使用 Conventional Commits 格式：

```text
<类型>: <简短说明>
```

类型只使用：

- `feat`：新增兼容功能
- `fix`：修复问题
- `docs`：只改文档
- `test`：只改测试
- `refactor`：不改变行为的重构
- `chore`：构建、依赖或维护调整

类型使用英文小写，主题可使用中文，控制在 50 个字符左右并直接说明结果；具体背景、影响和验证统一写在 PR 中。一次提交只表达一个完整意图，不把无关修改混在一起。

示例：

```text
fix: 修复飞书推送条数统计
docs: 补充部署排障说明
chore: 准备 v0.2.1 发布
```

## 版本规则

项目使用语义化版本 `MAJOR.MINOR.PATCH`，版本唯一来源是 `pyproject.toml`。

- `PATCH`：兼容性修复和稳定性改进。
- `MINOR`：新增向后兼容的能力。
- `MAJOR`：配置、接口或行为不兼容的变更。

正式版本发布时同步更新 `CHANGELOG.md`，创建带 `v` 前缀的 Git tag，并在 GitHub 创建 Release。普通修复提交不单独创建版本。

服务接口从已安装包元数据读取版本，不能在业务代码中重复维护版本常量。

## PR 要求

PR 正文按模板填写：变更目的、主要变更、影响范围、验证结果、版本和部署信息、风险与回滚方式。描述使用正常 Markdown 换行，不把整段内容写在一行。

标题沿用提交类型格式，例如 `fix: 修复飞书推送状态误报`。一个 PR 聚焦一个主题；若同时包含代码、测试和文档，应在“主要变更”中分别列出。

合并前必须满足：

1. CI 通过；
2. 版本变更与 `CHANGELOG.md` 一致；
3. 已完成的部署验证有命令和结果；
4. 不包含 `.env`、`data/`、真实密钥、服务器地址或运行日志。

## 发布顺序

```text
本地测试 → 主审核 → commit → 部署验证 → 用户确认 → push → PR → CI → merge → tag/Release
```

部署验证失败时不得创建正式版本 tag；修复应继续留在同一功能分支，直到验证通过。
