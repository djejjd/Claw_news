# 开发流程

## 目的

本流程将“为什么做、系统必须保持什么、这一版怎样落地、这次提交改什么”分开记录。实现者可以决定函数和模块组织，不能自行决定公开接口、数据状态、权限、默认值、失败语义或兼容性。

## 阶段与门禁

```text
需求/问题 -> 调研（按需） -> 设计 -> 版本开发方案 -> 任务包 -> 任务包启用 -> 测试先行实施 -> 审核 -> 发布/回顾
```

| 阶段 | 必要产物 | 通过条件 |
|---|---|---|
| 调研 | `docs/研究/` 记录（按需） | 关键事实、备选方案和未知项已区分 |
| 设计 | `docs/架构/` 领域设计或 `架构/决策/` | 稳定契约、边界、兼容性和非目标已批准 |
| 版本开发方案 | `docs/计划/<领域>/<版本>-开发方案.md` | 变更地图、依赖、任务分解、验证和退出条件完整 |
| 原子任务包 | `docs/计划/<领域>/<版本>/T*.md` | 文件边界、接口变更、测试矩阵和验收可直接实施 |
| 任务包启用 | `make task-gate TASK=<任务包路径>` 的通过记录 | 状态、设计基线、依赖完成证据和工作区范围均通过校验 |
| 实施与审核 | 代码、测试、PR | 测试先行、完整 diff 审核和质量检查通过 |
| 发布与回顾 | PR、CHANGELOG/Release（发布时）、归档记录（按需） | 用户批准的集成、部署和遗留项记录完成 |

## 批准与冻结

稳定设计必须在 front matter 或“决策与批准”表中记录 `状态`、批准角色、批准日期、设计基线和待决问题。状态遵循《文档规范》；只有 `approved`、待决问题为空且基线为不可变 Git commit SHA 的设计可被任务包引用。`draft` 和 `pending_approval` 只能用于讨论或准备任务包，不得启动代码实施。

用户可见的接口、默认值、权限、数据保留和错误语义由用户明确批准；纯内部且不改变已批准语义的实现细节可由用户指定的主审核者批准。设计变更必须增加修订记录、更新基线并重新批准。任务发现未决项、设计与代码冲突或无批准基线时必须停止实施。

## 风险分级

| 类型 | 最低要求 |
|---|---|
| 文档、测试、小型兼容修复 | 原子任务包 |
| 多模块功能、配置或运行状态变化 | 版本开发方案 + 原子任务包 |
| 公共 API、持久化、权限、安全、外部副作用、发布流程 | 领域设计 + 版本开发方案 + 原子任务包 |

设计、方案和任务包冲突时停止实施；未决定的用户可见语义必须回到设计阶段，不能作为 Agent 的临场选择。

## 任务状态与可执行门禁

每个原子任务包的 front matter `状态` 只能使用以下状态机，状态不是事后描述，而是编码和提交权限：

```text
draft -> ready -> active -> review_pending -> completed
```

| 状态 | 含义 | 允许操作 | 退出条件 |
|---|---|---|---|
| `draft` | 任务包仍在编写或存在未决项 | 仅修改任务包和设计讨论材料 | 十二段、精确文件边界、测试矩阵完整 |
| `ready` | 用户已批准任务范围，等待开始 | 仅核对前置条件和启用任务包 | 依赖完成、设计基线有效、用户或主流程明确启动 |
| `active` | 当前唯一可实施任务 | 运行 `make task-gate` 后才可修改实现和测试 | 失败测试、最小实现和任务检查完成 |
| `review_pending` | 实现完成，等待独立/主审核 | 只允许审核、修复审核 finding 和更新审核证据 | 主审核结论为 `approved` |
| `completed` | 已通过审核且已完成关闭记录 | 不再修改该任务范围；后续任务可引用 | 实现 commit 含 `Task: <任务编号>`；关闭记录填入其 SHA |

任务包元信息必须提供精确的仓库相对路径或 glob：`允许修改路径`、`禁止修改路径`、`设计基线`、`启动审查结论`、`主审核结论`和`任务提交`。自然语言“新增模块”不能替代可校验路径。依赖任务必须同时为 `completed` 且 `主审核结论` 为 `approved`，下游才可进入 `active`。

### 启动审查角色

每次任务从 `ready` 启用为 `active` 前，主实施 Agent 必须调用一个独立的“启动审查 Agent”。该角色不是常驻后台服务，而是任务开始时按固定清单执行的一次独立审查；这样既保留独立判断，也不会引入无人维护的长期进程。

启动审查只核对流程，不实现代码：已批准设计与基线、任务包十二段和接口变更表、依赖关闭记录、允许/禁止文件边界、并行冲突、分支/worktree 与干净工作区。它在任务包元信息写入 `启动审查结论：approved/rejected` 和简短证据。只有 `approved` 才能进入 `active`；`make task-gate` 会强制校验该字段。发现设计、任务包或代码基线冲突时结论必须为 `rejected`，实施停止并回到相应阶段整改。

### 开始门禁

在任何实现或测试编辑前，先将任务包更新为 `active`，再运行：

```bash
make task-gate TASK=docs/计划/<领域>/<版本>/T*.md
```

该命令校验当前分支不是 `main`、任务状态为 `active`、独立启动审查已批准、设计 SHA 在 Git 中存在、依赖任务已完成并通过审核，以及当前工作区仅含该任务的允许路径和任务包本身。失败时必须停止编码；不得以“稍后补文档”或“先写测试”为由绕过。

### 审核与提交门禁

实现完成后，先更新任务包为 `review_pending` 并记录完整检查结果，进行独立审核和整改。主审核批准后，创建实现提交；随后以一个只修改任务包及同版本开发方案的关闭记录，将任务包更新为 `completed` 并填入实现 commit SHA。关闭记录不得再包含实现或测试文件；门禁会验证该 SHA 存在且提交说明含对应 `Task:` trailer。PR 还会确认该实现提交属于当前 PR，已在目标分支关闭的任务不得再次声明。关闭记录完成前，不得启用下游任务。实现提交前运行：

```bash
make task-commit-check TASK=docs/计划/<领域>/<版本>/T*.md
TASK_PATH=docs/计划/<领域>/<版本>/T*.md git commit -m "feat: summary" -m "Task: vX.Y.Z-TN"
```

首次使用仓库时执行 `make install-hooks` 启用 `.githooks/`；pre-commit 和 commit-msg 会重复校验任务状态、暂存文件边界和 `Task:` trailer。PR 的 CI 从模板中的“任务包”字段读取路径，重新验证任务状态、设计基线、依赖和相对目标分支的文件范围。

## 文档模板

### 领域设计

放在 `docs/架构/`，描述跨版本稳定的事实。必须包含“决策与批准”表。涉及接口时必须包含：资源与可见性、接口变更表、每端点成功/失败 JSON、字段映射（类型、可空、来源、公开性）、错误表、数据与状态变化、时间/并发/安全边界、兼容性、非目标和修订记录。每条公共端点必须有方法、路径、调用者、认证、参数、成功码和失败码。

### 版本开发方案

放在 `docs/计划/`，描述本版本的实施组合。必须包含：目标和非目标、引用的设计、变更地图（端点/模块/存储/配置/调度）、任务依赖图、每项变更的负责人文件边界、测试与发布策略、退出条件和风险。端点、存储和配置三类变更必须 100% 映射到至少一个任务包。

### 原子任务包

保留仓库要求的十二段，但按以下内容填写：任务元信息；背景；目标；前置依赖；任务输入、交付物与行为契约；修改范围与接口变更表；禁止事项；执行要求；步骤；验收；检查；自检；交付格式。元信息必须填写可执行门禁所需的状态、依赖、设计基线、允许/禁止修改路径、主审核结论和任务提交字段。涉及 HTTP、模块或存储接口时，接口变更表必须列出新增/修改/保持不变项、参数、返回、错误、兼容性和测试文件。测试矩阵至少覆盖正常、边界、失败和最可能的反向回归；状态或统计必须有两次变化序列。

## 量化检查

- 设计：公共端点、公开 DTO 字段、错误码、状态转换均不得留空；设计中的每个接口必须有至少一个成功和一个失败示例。
- 方案：所有变更接口、存储表、配置项、调度入口都有任务归属；同一文件的并行修改为零。
- 任务：每个新增或修改接口都有契约测试；每个写入/清理路径都有成功、失败、重复执行测试；每条脱敏规则同时测试拒绝样本和合法相邻字段。
- 发布：所有退出条件有命令或人工证据；未验证内容有唯一待办、关闭条件和阻塞说明。

## 归档与学习

完成版本后，稳定结论回写架构文档；任务过程、已失效方案和复盘移入 `docs/归档/`。不以归档材料覆盖当前设计。
