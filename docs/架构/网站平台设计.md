## 1. 设计结论

Claw_news 后续扩展为“公共新闻网站 + 私有运营后台”。这不是在现有推送接口上加一个页面，而是新增内容发布、账户和订阅能力；现有采集、选材、LLM 摘要和消息推送继续作为内容生产内核。

第一版面向项目维护者和少量受邀用户，采用 Vue 3 + TypeScript 前端、FastAPI 后端和 PostgreSQL。先本地开发验证，再部署到现有单实例服务器。

## 2. 产品边界

### 2.1 公共网站

- 未登录用户可以浏览公共日报和最近 10 天的公开新闻。
- 公共日报由系统统一生成，所有用户看到同一版本。
- 新闻流展示当天完成规范化、去重、分类和规则相关性过滤后允许公开的候选，不要求每条调用 LLM；未经治理的原始候选不进入公开新闻流。
- 新闻有来源摘要时展示来源摘要；没有摘要时只展示标题、来源、分类、时间和原文链接。
- 普通新闻不调用 LLM；只有进入公共日报的精选新闻才进行 LLM 摘要和分析。

### 2.2 登录用户

- 管理员通过邀请创建账号，第一版不开放公开注册。
- 登录后默认进入“我的订阅”，也可以切换到“全部新闻”。
- 用户只管理来源订阅和取消订阅，不提供分类开关、优先级、关键词或自然语言要求。
- 订阅偏好只影响用户视图，不修改公共日报，也不触发重新采集或重新摘要。
- 新增来源默认不加入已有用户，由用户手动开启；管理员可以决定是否加入新用户默认订阅集合。

### 2.3 私有管理后台

- 管理员管理用户、邀请、来源配置和来源启停状态。
- 管理员查看采集、发布和推送状态，必要时执行已有的手动运行入口。
- 管理接口不得向普通用户暴露密钥、评分细节、候选池内部错误或未发布状态。

第一版暂不包含收藏、已读、个人消息通知、正文提取、公开注册和多管理员权限细分。

## 3. 总体架构

```text
Collectors -> Candidate Pool -> Selection -> LLM Summary
                    |                         |
                    v                         v
             全部新闻发布库              公共日报发布库
                    |                         |
                    +------------+------------+
                                 |
                         FastAPI API 层
                         /公共 /用户 /管理
                                 |
                         Vue 3 前端应用
```

- `CandidateItem` 是内部候选对象，不作为公共 API 契约。
- 新增公开 `Article`、`Digest` 和 `Source` 领域模型。
- 采集成功且去重后的候选写入新闻库；日报精选结果写入日报和摘要表。
- 网站查询只读发布库，不触发采集、LLM 或消息推送。
- 现有 JSON 状态文件可在迁移期保留，用于投递恢复和运行审计；业务内容逐步迁移到 PostgreSQL。

## 4. 核心数据模型

### 4.1 内容

- `articles`：稳定 ID、canonical_key、标题、原文链接、来源、最终分类（四类枚举 `ai/tool/game/digital`）、主题（`topic`/`topic_confidence`）、源摘要、发布时间、采集时间、可见状态。`device` 仅作输入兼容别名，不作为公开分类值。
- `digests`：自然日、发布版本、发布时间、生成状态和统一判断。
- `digest_items`：日报与文章的关联、排序、LLM 核心摘要、重要性、趋势、主题标签（`topic_label`）和 LLM 相关性分（`relevance`，终选值，用于审计）。GitHub 项目推荐（`github_projects`）与日报同事务写入，归 digest 级别。

文章状态至少包括 `published`、`hidden` 和 `expired`。只有 `published` 内容进入公共 API。按配置时区的自然日保留最近 10 天；第 11 天先将文章标记为 `expired`，再删除对应日报关联和文章记录，不做永久保留。日报与普通新闻使用同一保留窗口，清理按 `digest_items` 再 `articles` 的顺序执行。

### 4.2 来源

- `sources`：来源唯一名、展示名、默认分类（`default_category`，仅作采集兜底，不等同文章最终分类）、站点地址、启用状态、是否加入新用户默认订阅、创建和更新时间。
- `source_feeds`：具体 RSS/API 地址及采集器类型、策略参数、最近成功时间、最近失败时间、连续失败次数和最近错误摘要。区分 source 聚合健康与单个 feed 健康；瞬时失败不直接写成来源停用。

来源展示名与采集地址分离，用户按来源订阅，不感知底层 RSS 地址。管理员新增来源必须经过 URL、分类和策略校验。

### 4.3 账户与偏好

- `users`：邮箱/登录名、密码哈希、角色、状态、首次登录状态和时间戳。
- `invitations`：一次性 token 哈希、目标账号、过期时间（默认 24 小时）、使用时间和状态。
- `sessions`：会话 token 哈希、用户、过期时间、撤销时间和最近访问时间。
- `user_source_subscriptions`：用户、来源、订阅状态和更新时间。

密码只保存慢哈希，邀请和会话只保存 token 哈希。第一版角色保留 `admin` 和 `user`，先创建一个管理员，数据模型支持后续增加管理员。

## 5. API 边界

公共 API：

- `GET /api/public/digests?date=`：读取指定日期公共日报。
- `GET /api/public/articles?date=&source=&page=`：读取公开新闻流。
- `GET /api/public/sources`：读取可公开展示的来源摘要信息。

用户 API：

- `GET /api/me/subscriptions`、`PUT /api/me/subscriptions/{source}`。
- `GET /api/me/articles?...&view=subscribed|all`：按来源订阅过滤新闻。

认证与邀请 API：

- `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me`。
- `GET /api/auth/invitations/{token}`：只返回邀请是否有效，不返回 token 哈希。
- `POST /api/auth/invitations/{token}/accept`：一次性设置密码并激活账号；成功后立即轮换 Session。

管理 API：

- `POST /api/admin/invitations`、`GET /api/admin/invitations/{id}`、`POST /api/admin/invitations/{id}/revoke`。
- `GET /api/admin/users`、`POST /api/admin/users/{id}/disable`、`POST /api/admin/users/{id}/reset-invitation`。
- `GET/POST/PATCH /api/admin/sources`。
- `POST /api/admin/sources/{id}/test`、`GET /api/admin/runs`、`GET /api/admin/health`。

管理 API 必须服务端校验角色；公共 API 只返回发布字段，不直接序列化内部候选对象。

## 6. 认证与部署

- 使用服务端 Session + `HttpOnly`、`Secure`、`SameSite` Cookie；不把 JWT 放入 `localStorage`。登录成功和邀请接受后轮换 Session，停用用户时撤销其全部 Session。
- 所有 Cookie 写操作要求 CSRF token；登录接口增加限速和失败审计。开发环境允许 `Secure=false` 的 localhost 配置，生产环境强制 HTTPS、`Secure=true`。
- 开发环境前端与 API 可使用受控 CORS 和 `credentials`；生产环境推荐同一主域（例如 `news.example.com` 与 `/api` 反代），避免跨站 Cookie。
- Vue 静态资源独立构建和部署，FastAPI 只提供 API；生产环境由 Nginx/CDN 托管前端并将 `/api` 反代到 FastAPI。
- PostgreSQL 与应用先同机 Docker Compose 部署，保持单实例写入约束。
- 现有服务器（4 核、约 3.6 GiB 内存）可支撑第一版少量用户；Hermes 等现有服务占用较高，后续扩展前应监控 Swap，并将 8 GiB 作为升级基线。

## 7. 实施阶段

1. **内容发布基础**：PostgreSQL、迁移、`Article/Digest/Source` 模型，把采集和日报结果写入发布库。
2. **公共 API**：日报、10 天新闻流、来源列表和过期清理。
3. **Vue 用户端**：公共日报、全部新闻、登录、我的订阅和来源切换。
4. **账户与邀请**：Session、邀请链接、首次设置密码、停用账号。
5. **管理端**：来源 CRUD、用户管理、运行状态和权限校验。
6. **部署与观测**：Nginx、PostgreSQL 备份、日志轮转、磁盘/内存告警和发布验证。

## 8. 非目标与后续扩展

当前不引入全文搜索、推荐模型、个人 LLM 指令、收藏/已读、个人通知、多实例共享状态或复杂 RBAC。来源优先级、分类偏好、OAuth/OIDC、Passkey 和 PostgreSQL 独立部署作为后续扩展点。

## 9. 与现有系统的兼容原则

- 保持采集、选材、摘要和投递之间流水线接口可演进兼容；选材语义（分类、配额、评分、单源上限、摘要输入长度与 LLM 输出结构）按已批准治理版本迁移，字段与策略变化提供版本或迁移测试。
- 新增 `PublicationStore/Publisher` 适配层：采集成功的候选按 `canonical_key + fetched_at` 幂等 upsert 到 `articles`；日报选材和 LLM 完成后，在同一发布事务中写入 `digests` 与 `digest_items`，再执行消息渠道投递。
- 网站发布失败不得反向伪造消息推送成功；消息渠道失败也不得删除已经发布的网站内容。发布库写入失败时保留现有 JSON 状态并进入可重试状态。
- 现有 `IngestionStore`、`StateStore` 和 `publish_status.json` 在迁移期仍是运行审计与投递恢复来源；完成迁移后再评估是否停止业务内容写 JSON。历史 JSON 不自动全量回填，先从新发布周期开始，另行设计回填任务。
- 所有新数据库写入使用事务和幂等键；单源失败继续遵循现有 `safe_collect()` 隔离约定。
- `data/`、`.env`、真实邀请 token 和密钥不入库。

## 10. 查询、时间与来源迁移契约

- “当天”统一按 `config.tz` 的自然日解释；数据库时间保存带时区的 UTC，API 返回 ISO 8601 时间。
- 新闻流按 `published_at`（缺失时用 `fetched_at`）倒序，使用稳定 `id` 作为并列排序键；分页至少支持 `page`、`page_size`，上限由服务端控制。
- `source` 参数使用稳定来源名；隐藏、过期和未发布文章一律不返回。无源摘要时 `summary` 返回空字符串，不临时抓取正文。
- `articles.canonical_key` 建立唯一约束；同一 canonical_key 的重复采集按较新的有效发布时间、其次较新的采集时间更新公开记录，并保留最近一次来源摘要。
- 网站的“当天全部新闻”按 `fetched_at` 落在当地自然日判断，不套用推送流程中排除已发布 URL 的逻辑；重复折叠只按 canonical_key 进行。
- PostgreSQL 接入前先建立统一 `SourceRegistryAdapter`：将 `feeds.yaml`、`source_policies`、AI RSS 环境配置和 GitHub/TapTap/HuggingFace 非 RSS 来源转换为统一来源模型。迁移期间静态配置优先作为初始种子，数据库作为运行时唯一写入来源；评分常量仍由代码/策略契约管理，管理员只能修改允许的策略字段。
