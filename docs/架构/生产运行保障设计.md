# 生产运行保障设计

## 1. 背景、目标与非目标

网站上线前，部署成功不能等同于业务验收成功。现有服务的发布路径会写入候选池、跨次去重、摘要和投递状态，临时在生产调用发布接口会影响当天或次日的内容。因此 `v1.5.0` 除既定的部署与观测外，还必须提供部署准入、隔离演练和可持续维护能力。

目标：单实例环境可部署、备份、恢复、观测和回滚；每次部署有安装/配置/验收清单；真实采集、摘要和推送可在不影响生产状态的环境中演练；维护人员有明确的巡检、恢复和升级流程。

非目标：不修改内容选材规则、默认推送时间、消息格式、生产数据保留期限；不提交服务器地址、账号、密钥、私有脚本或生产数据；不引入多实例、高可用或跨区域部署。

## 2. 决策与批准

| 决策 | 契约 |
|---|---|
| 版本归属 | 所有内容属于网站 `v1.5.0 部署与观测`，在 `v1.0.0` 至 `v1.4.0` 功能验收后、首次生产验收前执行。 |
| 环境隔离 | 验收使用独立容器/运行目录、持久卷、数据库和 `.env`；验收模式必须显式设置 `RUN_MODE=acceptance` 与唯一的绝对 `STATE_ROOT`，不得挂载或复制生产 `data/`、生产数据库卷或生产渠道凭据。 |
| 生产验收边界 | 不得把生产 `POST /run/news` 用作验收。生产只允许启动、健康和只读状态检查；首次真实生产发布在正常调度窗口由值班人员确认。 |
| 部署准入 | 版本、质量、服务器依赖、配置、数据快照、调度排他性和验收环境均为部署前必检项；阻断项未通过即停止上线。 |
| 回滚 | 先暂停调度、保留日志和故障快照，再恢复已验收镜像/配置，必要时恢复部署前快照；禁止未保留现场直接删除 `data/`。 |
| 维护制度 | 每日巡检、每周容量与失败检查、每月隔离演练和恢复快照读取验证、每季度权限/来源/告警审查均需记录证据和异常关闭动作。 |

## 3. 环境、数据与安全边界

| 环境 | 数据与配置 | 推送目标 | 允许操作 |
|---|---|---|---|
| 本地开发 | 临时目录、Mock 或测试源 | 禁止真实渠道 | 单元、集成、回放 |
| 验收 | 独立卷、独立数据库、验收 `.env` | 专用验收群/机器人 | 端到端演练、部署验收 |
| 生产 | 唯一生产卷与数据库、生产 `.env` | 正式订阅者 | 定时运行、只读诊断、受控恢复 |

候选入库、`pushed_urls.json`、`published_keys.json`、日报摘要、待投递记录、来源状态、来源指标及 GitHub 快照均属于生产运行状态。`STATE_ROOT` 的语义是实际 `data/` 目录本身，而不是项目根目录；它是 JSON 状态、outbox、指标、GitHub 快照和健康读取的唯一根目录。所有持久化模块必须接收已解析的绝对 `STATE_ROOT`，禁止自行解析源码仓库路径或回退到默认 `data/`。迁移范围至少包括 `StateStore`、`IngestionStore`、`IngestStatusStore`、`SourceStateStore`、`SourceMetricsStore`、`GitHubStore`、`GitHubExposureStore`、`PendingDeliveryStore`、`PublicationRetryStore` 及 health/pipeline/scheduler 调用方。日常验收不得采用“备份、生产测试、回写”的方式：调度并发时回写可能覆盖有效状态。隔离运行是唯一常规验收路径；快照恢复只用于故障恢复。

渠道凭据的“生产/验收”归属不能从 webhook URL、token 或 host 自动推断。因此程序只强制 `RUN_MODE`、`STATE_ROOT`、独立数据库连接和显式验收渠道配置；验收 Compose 必须仅引用独立 secret-manager 条目或独立部署密钥。部署记录保存 secret 引用/版本或指纹的核验结论（不保存值）及验收群消息证据，并由运维确认其不等于生产引用。未能取得该证据时不得运行真实演练。

### 3.1 验收配置契约

`RUN_MODE` 只允许 `production` 或 `acceptance`。当 `RUN_MODE=acceptance` 时，配置加载器只读取白名单中的进程环境与验收 Compose 明确装载的 `.env.acceptance`，不得读取项目根 `.env`；同名白名单变量以进程环境为准，`.env.acceptance` 只在进程环境未设置时提供值。非白名单变量不参与验收运行。所有标准生产变量必须为空，包括 `LLM_*`、`WECOM_WEBHOOK_URL`、`TELEGRAM_*`、`FEISHU_*`、`PUBLICATION_ENABLED`、`PUBLICATION_DATABASE_URL`、来源控制变量和历史 `PUSHER_WECOM_WEBHOOK`。

验收模式只读取以下变量：

| 类别 | 变量与校验 |
|---|---|
| LLM | `ACCEPTANCE_LLM_API_KEY`、`ACCEPTANCE_LLM_BASE_URL`、`ACCEPTANCE_LLM_MODEL` 必填。 |
| 企业微信 | `ACCEPTANCE_WECOM_WEBHOOK_URL` 可选。 |
| Telegram | `ACCEPTANCE_TELEGRAM_BOT_TOKEN` 与 `ACCEPTANCE_TELEGRAM_CHAT_ID` 成对填写；`ACCEPTANCE_TELEGRAM_PROXY` 可选。 |
| 飞书 | `ACCEPTANCE_FEISHU_APP_ID`、`ACCEPTANCE_FEISHU_APP_SECRET`、`ACCEPTANCE_FEISHU_CHAT_ID` 三项成组填写。 |
| 发布库 | `ACCEPTANCE_PUBLICATION_DATABASE_URL` 必填，并在验收模式固定启用发布库；Alembic 在 `RUN_MODE=acceptance` 时只读取此变量，标准 `PUBLICATION_DATABASE_URL` 必须为空。 |
| 状态 | `STATE_ROOT`、`PRODUCTION_STATE_ROOT` 均为必填绝对路径且不得相等；前者是验收 `data/` 目录，后者只用于防止显式同路径配置。 |
| 应用与来源控制 | 标准应用变量 `TZ`、`NEWS_RSS_URLS`、`SOURCE_FAILURE_DEGRADED_THRESHOLD`、`SELECTION_DIVERSITY_PENALTY_PROFILE`、`TOPIC_CLUSTER_*`、`LLM_RELEVANCE_*` 和直接读取的 `HF_PROXY`、`HF_OPTIONAL`、`TAPTAP_OPTIONAL`、`AI_RSS_*`、`TOOL_RSS_*`、`GAME_RSS_*`、`DIGITAL_RSS_*`、`GITHUB_QUERY_BUDGET` 只允许以同名 `ACCEPTANCE_` 前缀变量提供；未设置时使用设计固定默认值，不得回退到标准变量。 |

至少一组验收渠道必须完整。生产模式只读取标准生产变量，进程环境仍覆盖项目 `.env`，必须拒绝任何非空 `ACCEPTANCE_*` 变量，防止部署身份混用。验收数据库、secret 和渠道的实际归属仍按上一段的人工门禁核验；变量前缀不构成身份证明。

## 4. 部署准入、验收与回滚

部署记录必须绑定目标 commit、镜像 tag、关联任务和回滚版本，并包含以下项：

| 类别 | 必须确认 | 未通过后的动作 |
|---|---|---|
| 质量 | 任务要求的测试、lint、格式、构建和未验证项 | 停止部署，修复或登记阻断项 |
| 依赖 | Docker/Compose、反代、端口、磁盘、时钟、时区和镜像来源 | 修复服务器条件后重新检查 |
| 配置 | `.env` 权限、LLM 必需项、渠道成组配置、生产/验收环境标识 | 不启动或不切换流量 |
| 数据 | 卷与数据库可读、部署前快照、迁移、备份一致性与恢复后应用可读性 | 不覆盖持久化数据 |
| 调度 | 仅一个调度来源，部署窗口无重复触发 | 暂停冲突调度 |
| 网络与会话 | HTTPS、反代到应用的可信头、生产 Cookie 标志、应用/数据库端口不对公网暴露 | 不切换流量 |
| 验收 | 验收环境、独立渠道、secret 引用核验和证据记录可用 | 不执行真实端到端验收 |

验收分为：生产启动与只读健康检查；验收环境端到端采集/摘要/渠道投递；验收内容质量；正常调度窗口的首次生产发布确认。功能性真实推送只允许发送到验收渠道；首次生产发布不是功能测试，而是在用户批准后确认正常调度、状态和正式消息均符合预期。验收环境不可用时，部署不得被描述为已完成真实推送验证。

## 5. 隔离端到端演练契约

演练唯一入口固定为 one-shot 命令 `python -m app.acceptance.run`，按“采集 -> 候选写入 -> 摘要 -> 至少一个验收渠道投递”执行。该命令不得启动 FastAPI lifespan、HTTP 服务或 APScheduler；验收 Compose 不得映射生产服务端口、不得启用自动重启调度。程序运行前只校验显式 `RUN_MODE=acceptance`、绝对 `STATE_ROOT`、验收数据库和验收渠道配置；数据库/渠道实际身份与凭据归属必须先由部署门禁人工核验，不能由程序根据 DSN、token 或环境变量声明推断。

启动前程序必须拒绝：非 `acceptance` 模式、任何非空标准生产变量、相对或空的 `STATE_ROOT`/`PRODUCTION_STATE_ROOT`、两状态根相等、缺失/不完整的验收 LLM、验收数据库或验收渠道配置。程序不得把任意 `SECRET_REFERENCE_VERIFIED` 一类声明当作身份证明，也不得声称能识别生产数据库连接。secret 引用/版本或指纹的差异、验收数据库身份和验收群消息必须在运行前由运维核验并记录为部署门禁证据。每次演练前后都记录验收卷快照；自动化测试必须覆盖进程环境覆盖 `.env.acceptance`、标准/验收变量不回退、正常演练、可验证的上述拒绝路径、服务启动时 scheduler 为零、未经 one-shot 命令零写入/零投递、失败后无状态外溢及连续两次演练。测试须枚举全部状态产物并同时比对生产状态目录的内容和元数据不变。

现有实现没有该入口。T3 将测试先行实现，不得以现有 CLI `dry-run` 或生产 `/run/news` 伪称满足本契约。

## 6. 维护与证据

| 频率 | 工作 | 证据与关闭条件 |
|---|---|---|
| 每日 | `/health`、最近采集/发布、来源失败、摘要条数/分类/来源、渠道状态 | 巡检记录；异常有唯一待办、负责人和影响说明 |
| 每周 | 日志、磁盘/卷增长、数据库备份、待重试记录、连续来源失败、配置权限 | 已处理、已升级或有完成日期 |
| 每月 | 验收环境端到端演练、快照可读取、部署清单复核 | 演练/恢复证据；失败为阻断性风险 |
| 每季度或重大变更前 | 密钥轮换、来源与渠道、告警阈值、回滚时长审查 | 审查记录与后续任务 |

维护手册必须区分只读、可逆和破坏性操作。删除候选、清空运行数据、恢复快照、轮换凭据或调用真实发布接口均须注明授权角色、前置快照、影响范围和完成验证。

## 7. 兼容性、测试与修订

生产默认行为、API 路径、时区、选材和投递语义保持不变。新增验收模式不得默认启用，也不得从生产环境变量推断。T1-T5 的测试矩阵必须覆盖正常、边界、失败和反向回归；所有真实外部依赖的人工验收均须留证，不得用 Mock 标记完成。
