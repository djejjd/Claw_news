## 1. 背景与目标

当前每天输出的摘要存在两个体验问题：**单一来源占比过大**、**部分推荐与主题相关性偏弱**。本文基于生产环境（`124.223.102.241`）的真实运行数据定位根因，给出分层的治理方案，而不是针对某个具体来源打补丁。

**目标**：每天稳定输出 10 条「来源多元、主题相关、分类正确」的摘要；任何单一来源占比不越过红线；任何分类不出现主题漂移。

**原则**：

1. 治理下沉到根因，不在输出端打补丁；
2. 规则可配置、可观测、可回滚，不硬编码进业务逻辑；
3. 先量化、再改动、后验证（改前留基线，改后有对照）；
4. 单源故障不阻断全流程（延续现有 `safe_collect` 隔离）。

## 2. 现状诊断（生产真实数据基线）

数据来源：`data/ingestion/`（候选池）、`data/*/ai_digest.json`（已发布摘要）、`data/pending_deliveries/`、`data/source_metrics/`（88 天采集指标）。

### 2.1 来源占比：IT之家一家独大

候选池近 7 天（2026-08-08 ~ 08-14）来源分布：

| 来源 | 候选数 | 占比 |
|---|---|---|
| **ithome（IT之家）** | **1211** | **74.7%** |
| gcores | 74 | 4.6% |
| huggingface | 63 | 3.9% |
| leiphone | 59 | 3.6% |
| qbitai | 47 | 2.9% |
| 其余 9 源 | 168 | 10.4% |

历史已推送（12 份 digest + 31 份 pending，共 201 条）来源占比：

| 来源 | 条数 | 占比 |
|---|---|---|
| **ithome** | **128** | **63.7%** |
| qbitai | 14 | 7.0% |
| leiphone | 8 | 4.0% |
| gcores / sspai / appinn / chuapp / yystv / eurogamer / huggingface | 其余 | 1%–3.5% 不等 |

> **口径说明**：63.7% 是「历史累计」数，主要来自 07-14 ~ 08-11 的 pending 记录（source-cap 修复前，该时段 ithome 占比约 81%）。08-12 已做过一次来源上限调整，08-12 / 08-13 两期已发布摘要为 7 个来源、每源 ≤2，无单源霸榜。故「霸榜」是历史问题，当前已在改善，仍需制度化防止复发。另外旧格式 digest（05-18~07-09）无 `source`/`topic` 字段，属数据迁移缺口，已从上表剔除，不再计入来源占比。

### 2.2 采集失衡：多样性源长期断供（且 TapTap 有双重故障）

`source_metrics`（88 天累计）：

| 源 | 累计运行 | raw 抓取 | 接受 | 失败率 |
|---|---|---|---|---|
| rss（全部 RSS 源） | 4177 | 174,655 | 9,495 | ~2% |
| **huggingface** | 4177 | 950 | 63 | **90%** |
| **taptap** | 1739 | 760 | **0** | **94%** |

- **huggingface**：90% 时间报错，长期缺位。
- **taptap**：是**双重故障**——① 94% 时间网络报错；② 即使抓取成功（95 次 ok、760 条），也 **100% 被拒（accepted=0）**。根因：`collectors/taptap.py` 构造的 `HotItem(summary="")` 摘要恒为空，被 `app/ingest/source_policy.py` 的 `should_accept_candidate`（要求摘要长度 ≥ 5）全部拦下。这条不修，TapTap 永远进不了候选池。

> 补充：HuggingFace / TapTap 的网络失败最近已修复。`docker logs`（08-14）显示当前每轮 ingest 均正常返回（rss 128、huggingface 10、taptap 10、github 33–37）。但 TapTap 的「摘要恒空被拒」问题仍未修复，候选池的存量失衡也会延续一段时间。

### 2.3 分类漂移：数码/AI 内容被塞进「工具」

IT之家在 `feeds.yaml` 里整站写死为 `tool`，但其内容大量是 AI / 数码 / 汽车 / 法律新闻，入选后全顶着「工具」标签，例如：

- `[工具] IT早报 0710：OpenAI 发布 GPT-5.6 系列模型`（实为 AI）
- `[工具] 华为李文广回应友商智驾兜底…`（实为汽车/智驾）
- `[工具] 苹果起诉OpenAI，指控其挖角前员工…`（实为法律/AI）
- `[工具] 古尔曼：苹果将跳过 M6 Pro/Max 芯片…`（实为数码）

根因：产品定位是「AI、工具、游戏、数码」四类，但代码只有 `ai/tool/game` 三类，`device（数码）` 被 `device→tool` 别名并入了「工具」。

### 2.4 主题性弱

当前（08-12 / 08-13 已发布摘要）主题分布：

| 主题 | 条数 |
|---|---|
| 产品（`application_case`，兜底主题） | 多数 |
| 工程 / 开源 / 模型 / Agent | 少数 |

> **口径说明**：早前统计的「72% 无主题/兜底」包含 05-18~07-09 的旧格式 digest（那时尚无 topic 字段，`topic=None` 被记为「无主题」），属于数据迁移假象，不能代表当前问题。当前真实问题是：`TopicClassifier` 只覆盖 AI，tool/game 没有主题判断，导致这两类内容只能落到兜底主题「产品」。

### 2.5 相关性过滤漏放

相关性拒绝记录（近期已发布 digest 累计 207 条）：`below_threshold` 171、`rule_conflict` 27、`negative_rule` 9。

关键词过滤确实在干活，但 IT之家快讯标题里塞满 `AI`/`模型`/`发布` 这类宽泛正向词，而 strict 档位等于「命中 1 个宽泛词即 0.7 放行」，所以大量快讯漏过。

### 2.6 token 消耗未优化

候选池 1622 条实测长度：

| 字段 | 中位 | 平均 | P90 | 最大 |
|---|---|---|---|---|
| 标题（字符） | 38 | 41 | 57 | 170 |
| 摘要（字符） | 542 | 838 | 1555 | **21,925** |

`llm.py` 未对摘要做截断，整段 RSS 摘要直接喂给 LLM（最长 2.2 万字），是 token 消耗的大头。

## 3. 已定决策

| 决策项 | 结论 |
|---|---|
| 单源占比红线 | **≤25%**（连续 7 天） |
| 单源单次上限 | **快讯源（IT之家/V2EX/cnBeta）≤2 条，其余源 ≤3 条** |
| LLM 相关性兜底 | **方案 A**（并入现有摘要调用，输出加 `relevance` 分） |
| 分类体系 | **4 类 `ai / tool / game / digital`**（数码从工具拆出） |
| 来源扩展 | **全接实测可达源**，分 Phase 1/2 分批上 |
| 分类保底配额 | **`ai:3 / tool:2 / game:2 / digital:0`**（数码不保底，纯竞争） |
| 采集失败观测 | 按 feed 维度落盘失败原因，支持精确回溯 |

## 4. 分层治理方案（L0–L4）

按数据流分层，每层解决一类问题，互不越界：

```
采集层 L0 ──► 分类层 L1 ──► 选材层 L2 ──► 摘要层 L3 ──► 运营层 L4
(来源治理)   (分类/相关性)   (多样性/评分)   (LLM兜底)   (调优闭环)
```

### L0 采集层 —— 来源治理

1. **来源健康度告警（一等公民）**：连续 N 次失败的源，在 `/health` 和推送里标记 `degraded`，让「多样性源断供」可见。现有 `source_state` + `source_metrics` 做底子。
2. **修复 TapTap 摘要恒空**：给 TapTap 的 `HotItem` 填上非空摘要（游戏简介），否则永远被 `should_accept_candidate` 拒掉。
3. **按 feed 落盘失败原因**：`failed_feeds` 目前只写日志和 `skipped_sources`，改为按源持久化到 metrics，支持精确回溯「哪个 feed 老失败」。
4. **来源扩展按「缺口」补**：见第 6 节，只接入实测可达的源；每源先验证「可达性→更新频率→内容质量→分类归属→失败可跳过」再进正式配置。

### L1 分类层 —— 分类与相关性

1. **内容级动态分类**：RSS 源保留默认分类作为兜底，正式分类在候选入池后由分类器按内容重判（针对 IT之家这类综合源）。
2. **全类别主题分类**：把 `TopicClassifier` 从只覆盖 AI，扩展到 tool/game/digital 各一组主题桶，让这三类不再全落兜底主题「产品」。
3. **相关性规则收紧**：拆解 `ai`/`模型`/`发布`/`研究` 等宽泛正向词；strict 通过逻辑从「单命中即过」改为「需 ≥2 个独立信号」；扩充负面词（促销/汽车/家电/话费/票房/法律/公司人事/天气等）。

### L2 选材层 —— 多样性与评分

1. **统一单源上限**：`max_selected_per_digest` 变为「所有源默认值 + 可覆盖」——快讯源（IT之家/V2EX/cnBeta）≤2，其余 ≤3。
2. **多样性惩罚指数化**：`_PENALTY` 从线性温水（0/-1/-2/-3.5/-5）改为随已选数指数增长（如 0/-1/-3/-6/-10），让已多次入选的源真正失去竞争力。
3. **评分再平衡**：缩小 `quality_weight` 绝对差距，提高 freshness 占比；freshness 加连续衰减（现在只有 24/48/72 三档台阶）。
4. **同主题聚合去重**：对入选候选做标题/链接相似度聚类，同一热点多源只留一条，避免刷屏。
5. **分类配额可配置化**：`_CATEGORY_MINIMUMS` 从硬编码改为可配置，当前为 `ai:3 / tool:2 / game:2 / digital:0`。

### L3 摘要层 —— LLM 兜底

见第 7 节。核心：让 LLM 输出 `relevance` 分做相关性兜底（方案 A，零边际成本），并把摘要截断到 ~200 字。

### L4 运营层 —— 调优闭环

1. **每日自动回放 + 来源分布报表**：复用 `scripts/replay-content-selection.py`，每天跑一次，输出来源/分类/拒绝分布，超标自动告警。
2. **每周 review**：用数据驱动调整 L0–L2 参数，而不是靠感觉。

## 5. 分类体系设计 v2

### 5.1 四类运行时分类

| runtime key | 显示 | 定位 | 典型来源 |
|---|---|---|---|
| `ai` | AI | 模型 / Agent / 研究论文 / AI 应用与行业 | qbitai、leiphone、HF、arXiv、InfoQ、meituan_tech |
| `tool` | 工具 | 开发/效率：软件、开源项目、IDE、框架、命令行、效率 App | sspai、appinn、OSCHINA、V2EX、HN、cloudflare_cn、GitHub |
| `game` | 游戏 | 新游 / 电竞 / 评测 / 行业动态 | yystv、gcores、chuapp、indienova、eurogamer、GamesIndustry |
| `digital` | 数码 | 消费电子：手机、电脑、芯片、硬件、OS、数码评测 | ithome、cnBeta、9to5Mac、TechCrunch、威锋 |

关键点：把「数码」从「工具」里拆出来独立成类，直接解决 IT之家/少数派的数码、AI、汽车、法律新闻被整体塞进「工具」的问题。

### 5.2 分类保底配额（10 条里，可配置）

```
ai: 3    tool: 2    game: 2    digital: 0   → 保底 7 条 + 3 条自由竞争
```

`digital` 不保底（`0`），纯自由竞争：数码新闻价值低、易刷屏，只在自由竞争阶段凭分数进入，不占用保底名额。

### 5.3 改动文件清单

| 文件 | 改动 |
|---|---|
| `app/category_policy.py` | `RUNTIME_CATEGORIES` 加 `digital`；`DISPLAY_CATEGORY_MAP` 加 `digital→数码`；别名 `device→tool` 改为 `device→digital`（存量数据兼容） |
| `app/pipeline/selection.py` | `_CATEGORY_MINIMUMS`、`_CATEGORY_ORDER` 扩成四类，配额 `ai:3/tool:2/game:2/digital:0` |
| `feeds.yaml` | 每源写默认分类（新增 digital 分类），允许分类器在采集后改写 |
| `app/classifiers/relevance_filter.py` | 新增 `digital` 的 positive/negative 词表（负面词重点排除汽车促销、家电、话费、票房） |
| `app/classifiers/topic_classifier.py` | 给 tool/game/digital 各加一组主题桶 |
| `app/tools/llm.py` | prompt 从「AI 新闻分析师」改为覆盖四类的通用摘要指令 |

## 7. LLM 相关性兜底与 token 估算

### 7.1 现状基线（一次摘要调用，量级估算）

token 系数按中英混合 0.5–1.0 token/字符估算（具体取决于模型分词器）。

| 项 | token 估算 |
|---|---|
| 输入：10 条 ×（标题 ~40 + 摘要 ~500–850） | ~5,000–9,000 |
| 输出：10 条摘要 + daily_judgement | ~900–1,000 |
| **合计每次** | **~6,000–10,000** |

摘要长度是最大变数：中位 542 字、P90 1555 字、最大 21,925 字，未截断时单条即可吃掉数万 token。

### 7.2 三种兜底方案对比

| 方案 | 增量输入 | 增量输出 | 每次成本 | 结论 |
|---|---|---|---|---|
| **A. 并入现有摘要调用**（输出加 `relevance` 字段） | 0（复用） | +50 | ≈0（+1%） | ✅ 已定 |
| B. 独立对候选池「仅标题」打分 | 120×40=~5,000 | 600 | +5,600 | 备选 |
| C. 独立对候选池「标题+完整摘要」打分 | 120×900=~108,000 | 600 | +108,000 | ❌ 不可行 |

### 7.3 月度成本（30 次/月，国内主流 OpenAI-compatible 模型）

- 方案 A：增量 ~3,000 token/月 → **基本免费（<¥0.01/月）**；
- 方案 B（仅标题）：+17 万 token/月 → ~¥0.2–0.5/月。

### 7.4 结论

1. **采用方案 A**：把相关性判断并入现有摘要调用，让 LLM 对每条输出 `relevance` 分，低于阈值淘汰。零边际成本，同时解决「LLM 被禁止筛选」的问题。
2. **摘要截断到 ~200 字**：RSS 摘要里 80% 是废话（LLM 只输出 25 字 core_summary），这一刀能把现状 token 成本砍掉约 60%。

| **Phase 1（快赢）** | 统一单源上限（快讯 2/其余 3）、摘要截断、负面词扩充、修复 TapTap 摘要恒空、HF/TapTap 健康告警、按 feed 落盘失败原因 | 配置 + 少量代码 | 1–2 天 |

## 9. 风险与回滚

- **动态分类误判**：先只对「综合快讯源」启用重分类，其他源保持默认，灰度观察。
- **LLM 兜底成本/延迟**：方案 A 成本可忽略；做成开关 + 阈值可配，默认关闭，验证后再开。
- **上限过严导致候选不足**：上限是「软目标」，不足时按现有历史补位逻辑降级填充，不虚构内容。
- **分类体系 v2 迁移**：`device→digital` 别名保留，存量数据不破坏；新增分类需同步测试与文档。
- **每步有对照**：改前跑一次回放留基线，改后跑同时间点回放对比来源/分类/拒绝分布。

---

## 10. 验收标准

1. 任一单一来源在连续 7 天推送中占比 ≤ 25%（与「快讯源 ≤2 条」一致，2/10 = 20% < 25%）；
2. tool/game/digital 不再全落兜底主题「产品」，主题命中率提升；
3. 「工具」分类中非工具内容（AI/数码/汽车/法律）占比 < 10%；
4. TapTap 候选能进入候选池（accepted > 0），HF/TapTap 连续失败时 `/health` 能反映 `degraded`；
5. 每条改动有回放对照证据，`make test` + `make lint` 通过。
