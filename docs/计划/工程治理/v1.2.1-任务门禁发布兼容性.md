# v1.2.1 任务门禁发布兼容性方案

本方案归属 v1.2.0 之后的下一个 PATCH 版本，仅修复发布与多任务 PR 的兼容流程；不修改 `pyproject.toml`、`CHANGELOG.md` 或正式版本代码。

## 1. 问题与根因

v1.2.0 发布 PR 同时包含多个已完成任务的实现、关闭记录、版本文件和前端构建入口。当前 CI 将相对目标分支的全部变更交给每个任务包单独做允许路径校验，任务包之间没有发布语义，导致历史任务文档或版本文件被误判为单任务范围外改动。现有逻辑适合单任务 PR 和多任务实现 PR，不适合“功能已经合并、发布任务只做版本准备”的发布 PR。

## 2. 目标与非目标

目标：

- 保持常规单任务和多任务 PR 的严格路径并集校验。
- 增加显式发布 PR 模式，发布任务只校验发布增量；历史已关闭任务作为依赖证据，不重复参与实现范围校验。
- 保持任务状态、依赖、设计基线、启动审查、主审核、提交 trailer 和目标分支关系校验。

非目标：不修改业务代码、公开接口、版本号、部署行为或已发布 tag；不通过隐式分支名、环境变量或通配白名单绕过门禁。

## 3. 设计决策（已批准）

| 决策 | 方案 | 原因 |
|---|---|---|
| 任务类型 | 新发布任务包元信息必须显式声明 `任务类型：发布`；本 T1 显式声明 `常规`；仅当历史任务提交已是目标分支祖先且未作为当前 PR 任务声明时，缺失字段兼容解释为 `常规` | 使发布任务可机器识别，同时不阻断已关闭历史任务 |
| PR 模式 | PR 正文显式声明 `门禁模式：常规任务` 或 `门禁模式：发布 PR` | 使 CI 行为可追溯，拒绝隐式降级 |
| 常规多任务 | 对声明任务的允许路径和任务包路径取并集 | 支持一个 PR 串行集成多个原子任务，保留范围边界 |
| 发布 PR | 必须且仅能包含一个 `任务类型：发布` 任务；只校验该任务的允许路径、任务包和版本计划路径 | 不重新审查已在目标分支关闭的历史实现任务 |
| 发布任务约束 | 必须 `completed`、主审核 approved，提交在当前 PR；混入业务路径失败 | 发布模式不是总开关，仍需完整发布证据 |
| 缺省行为 | 缺少/未知/重复门禁模式直接失败；未知/重复任务类型或模式与任务类型不匹配失败；当前 PR 声明任务缺失类型直接失败 | 避免 CI 因旧正文静默选择宽松路径 |

## 5. 依赖、发布与回滚

- 依赖 `v0.2.2-T1` 完成；T1 只能在本方案和任务包通过启动审查后进入 `active`。
- 本治理版本本身不修改正式版本号，不创建 tag、Release、部署或外部推送。
- 回滚方式为 revert T1 实现提交并恢复 CI 旧调用；不回滚已发布的网站代码或版本记录。

## 6. 历史关闭任务与发布增量规则

- `常规任务` 模式对声明任务取允许路径并集；当前 PR 声明任务缺少 `任务类型` 直接失败。只有任务提交 SHA 已是目标分支祖先、且任务未作为当前 PR 声明任务时，历史任务缺失类型才兼容解释为 `常规`；未知或重复字段失败。
- `发布 PR` 模式的正文必须声明且仅声明一个 `任务类型：发布` 的已完成任务；`ci` 只对该发布任务执行提交、依赖和发布增量路径校验。
- 发布 PR 的增量只能包含发布任务允许路径、发布任务包及其版本计划路径；历史功能任务提交已经在目标分支关闭，不再次作为当前 PR 任务校验，也不得通过全局白名单放行历史业务文件。
- 发布 PR 必须从包含历史功能合并提交的目标分支创建；若差异中出现历史业务实现文件，门禁失败并要求重新拆分 PR。
