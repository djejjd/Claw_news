## 1. 目的与版本基线

当前独立推送服务的版本为 `v0.2.1`。网站不是现有 HTTP 服务的页面附加项，而是新增发布库、公共内容、账户和运营能力，因此网站首个可发布版本从 `v1.0.0` 开始。

本文只定义版本间的目标、依赖和验收边界。每个版本开始实施前，必须另建符合仓库十二段要求的实施任务包；任务包应引用本文和《网站平台设计》，并按测试先行执行。本文不授权直接修改业务代码、提交、推送或部署。

## 2. 总体依赖

```text
v1.0.0 内容发布基础
  -> v1.1.0 公共内容 API
    -> v1.2.0 公共网站
      -> v1.3.0 账户与订阅
        -> v1.4.0 运营后台
          -> v1.5.0 部署与观测
```

内容治理 Phase 1 和 Phase 2 已完成：四分类、内容级分类、来源策略、发布准入和 feed 健康基线已可作为网站发布模型的输入契约。Phase 3 的算法增强可独立推进，但不得破坏上述发布契约，也不阻塞 `v1.0.0`。

## 3. 版本划分

### v1.0.0 内容发布基础

**目标**：建立供网站读取的 PostgreSQL 内容发布库，使既有采集和日报流水线可可靠地发布规范化内容。

**前置依赖**：当前四分类、过滤后准入和来源上限语义；单实例写入约束。

**范围**：

- PostgreSQL 本地/测试连接配置、迁移框架和连接健康检查；生产 Compose、备份和发布配置留在 `v1.5.0`；
- `Article`、`Digest`、`DigestItem`、`Source`、`SourceFeed` 的模型、约束和仓储接口；
- `SourceRegistryAdapter`，统一静态 feeds、环境配置和非 RSS 来源的稳定来源标识；
- 采集候选和日报结果的幂等发布写入，使用 `canonical_key`、自然日和发布版本等稳定键；
- 发布事务、失败可重试状态和与现有 JSON 审计/消息投递的故障隔离。

**不做**：公共查询 API、前端、账号、管理页面、历史 JSON 全量回填。

**退出条件**：新发布周期可将允许公开的文章及日报写入数据库；重复运行不产生重复内容；数据库写入失败不会伪造消息投递成功，也不会删除既有运行审计。

### v1.1.0 公共内容 API

**目标**：提供仅查询发布库的稳定公共接口。

**前置依赖**：`v1.0.0` 发布库、迁移和基础发布链路验收通过。

**范围**：

- `GET /api/public/digests?date=`、`GET /api/public/articles?date=&source=&page=`、`GET /api/public/sources`；
- 仅返回 `published` 内容，按配置时区解释日期，实施稳定排序和受控分页；
- 最近 10 天的过期清理，以及公开字段和内部审计字段的隔离；
- API 契约、异常响应和数据库查询测试。

**不做**：浏览器界面、登录、订阅写入、管理接口；查询请求不触发采集、LLM 或消息推送。

**退出条件**：未登录客户端可稳定读取公共日报、新闻流和来源列表，隐藏、过期、未发布内容及内部评分/错误不泄露。

### v1.2.0 公共网站

**目标**：交付建立在真实公共 API 上的 Vue 3 + TypeScript 浏览体验。

**前置依赖**：`v1.1.0` 公共 API 已定型并具备契约测试。

**范围**：

- 公共日报首页、最近 10 天新闻流、来源筛选、原文跳转和加载/空/失败状态；
- 桌面与移动端的可读布局；
- 前端 API client、路由和端到端核心浏览路径测试。

**不做**：登录、订阅、收藏、已读、个人推荐、正文抓取和公共注册。

**退出条件**：未登录用户可在真实数据上完成日报浏览、新闻分页和来源筛选；前端不依赖模拟数据或直接读取内部候选池。

### v1.3.0 账户与订阅

**目标**：在邀请制前提下提供安全的账户和按来源订阅的个人视图。

**前置依赖**：`v1.1.0` 的用户查询边界与 `v1.2.0` 的公共前端基础。

**范围**：

- `users`、`invitations`、`sessions`、`user_source_subscriptions` 数据模型和迁移；
- 邀请验证与接受、登录、退出、当前用户、Session 轮换、停用撤销；
- `HttpOnly` Cookie、CSRF、登录限速和失败审计；
- 我的订阅、来源开关和按订阅过滤的新闻流。

**不做**：公开注册、OAuth/OIDC、Passkey、分类偏好、关键词偏好和个人 LLM 指令。

**退出条件**：受邀用户可以安全设置密码并登录；其订阅只影响个人视图，不修改公共日报、采集或摘要。

### v1.4.0 私有运营后台

**目标**：使管理员能在权限边界内维护来源和受邀用户，并查看运行状态。

**前置依赖**：`v1.3.0` 认证、角色校验和来源发布模型。

**范围**：

- 邀请、用户启停和重新邀请管理；
- 来源及 feed 的新增、修改、启停、测试和输入校验；
- 采集、发布、投递和来源健康状态的管理查询；
- 管理端界面和服务端角色授权测试。

**不做**：多管理员层级、复杂 RBAC、页面触发回放/重新选材、向普通用户展示运行错误或评分细节。

**退出条件**：管理员可完成来源和用户日常维护；所有管理写操作均经服务端鉴权、审计并避免暴露密钥与内部候选信息。

### v1.5.0 部署与观测

**目标**：让网站、API 和数据库在现有单实例服务器上可部署、备份、恢复和监测。

**前置依赖**：`v1.0.0` 至 `v1.4.0` 功能验收；现有服务资源评估。

**范围**：

- Docker Compose 中的 PostgreSQL、持久卷、备份和恢复演练；
- Nginx 或等效同域反代、HTTPS 和静态资源部署；
- 日志轮转、磁盘/内存/Swap、数据库连接和发布失败告警；
- 发布前检查、回滚步骤和生产验证清单。

**不做**：多实例写入、跨区域高可用、独立数据库集群和 CDN 优化。

**退出条件**：单实例环境可完成可验证部署和恢复；生产 Cookie 安全配置、备份、告警和回滚流程均有演练证据。

## 4. 每个版本的任务包要求

每个版本不以单一“大任务”实施，而是在启动前拆为可审查的小任务。任务包必须明确任务编号、依赖、允许并行项、预计/禁止修改文件和完成状态，并包含背景、目标、输入输出契约、修改范围、禁止事项、执行要求、步骤、验收、检查、自检和交付格式。

建议的拆分顺序如下：

| 版本 | 首批任务包方向 |
|---|---|
| `v1.0.0` | 数据库基础与迁移；领域模型与仓储；来源注册适配；发布流水线接入；发布回归与迁移验证 |
| `v1.1.0` | 公共读取仓储；日报 API；新闻流分页与清理；来源 API；API 契约测试 |
| `v1.2.0` | 前端工程；日报与新闻流；来源筛选；响应式与端到端验证 |
| `v1.3.0` | 认证数据与会话；邀请流程；订阅 API；登录与我的订阅界面；安全回归 |
| `v1.4.0` | 管理授权；来源管理 API；用户/邀请 API；运行状态 API；管理端界面 |
| `v1.5.0` | Compose 与反代；备份恢复；监控告警；生产发布验证 |

任务间有共享模型或数据库迁移时，必须先完成依赖任务的主审核；同一迁移文件、同一发布流水线入口和同一前端路由不允许并行修改。

## 5. 版本发布规则

- 开发分支从最新 `main` 创建；多文件功能默认使用独立 worktree 评估后实施。
- 每个任务先提交测试，再写最小实现；每次任务级 commit 前都须由主审核 AI 检查完整 diff。
- 版本完成后按 `make test`、`make lint`、格式检查和公开边界检查执行；涉及前端或部署时补充对应的构建、API/端到端和恢复验证。
- 只有用户明确同意后，才允许合并、推送、创建 tag 或部署；`pyproject.toml` 与 `CHANGELOG.md` 仅在正式版本发布任务中同步更新。
