## 1. 背景

当前采集候选、日报和投递审计存放在本地 JSON 文件中。网站需要一个供后续只读 API 查询的 PostgreSQL 发布库，同时保留 JSON 状态作为迁移期的投递恢复和运行审计来源。

## 2. 目标

建立可迁移的发布库、统一来源注册适配和 `PublicationStore/Publisher`，将过滤后允许公开的候选及日报终选结果幂等写入数据库。数据库写入与消息投递相互隔离，任何失败均可见且不伪造成功。

## 3. 前置依赖

- 四分类运行时契约为 `ai/tool/game/digital`，`device` 仅输入兼容别名；
- 公共新闻流只接收规范化、去重、分类和规则相关性过滤后允许公开的候选；
- 当前单实例写入模型和现有 JSON 审计、待投递恢复机制；
- `v1.0.0` 仅提供本地和测试数据库接入，不引入生产 Compose、备份或外网部署。

## 4. 输入与输出契约

输入：`CandidateItem`、选材结果、`SummaryResult`、GitHub 推荐、来源有效配置、配置时区。

输出：

- `articles` 以 `canonical_key` 唯一，按较新的有效发布时间、其次较新的采集时间更新；
- `digests` 以自然日和发布版本唯一；`digest_items`、GitHub 推荐与日报在同一事务写入；
- `sources` 使用稳定来源名，`source_feeds` 保存 feed/API 和健康字段；
- 数据库不可用或未启用时返回显式发布状态，既有 JSON 审计和消息投递不被删除或伪造。

时间在数据库保存为带时区 UTC；自然日依据 `config.tz` 计算。文章状态仅允许 `published`、`hidden`、`expired`。

## 5. 修改范围

1. 引入 SQLAlchemy、Alembic 和 PostgreSQL 驱动，提供 PostgreSQL 生产目标与 SQLite 测试替身。
2. 增加 `PUBLICATION_DATABASE_URL` 与显式 `PUBLICATION_ENABLED` 配置校验；启用时 URL 必填。
3. 新增迁移、领域 ORM 模型、仓储和发布器。
4. 新增 `SourceRegistryAdapter`，将 RSS、环境覆盖、HuggingFace、TapTap 等运行时来源映射为稳定来源及 feed。
5. 在高频采集完成过滤后发布文章；在 LLM 完成后同事务发布日报、日报项和 GitHub 推荐，再尝试消息投递。
6. 补充单元、迁移和流水线集成测试，并同步开发文档和示例配置。

## 6. 禁止事项

- 不实现公共、认证或管理 API，不增加 Vue 工程；
- 不自动全量回填历史 JSON；
- 不在数据库查询时触发采集、LLM 或投递；
- 不修改选材、评分、分类、相关性或消息格式语义；
- 不将真实数据库 URL、密钥或运行数据提交入库；
- 不以吞异常或“默认成功”掩盖发布库写入失败。

## 7. 执行要求

- 每项行为先写失败测试，再写最小实现；
- 所有数据库写入使用事务和幂等键；
- 开启发布库时，发布失败写入运行错误并保持 JSON/消息状态独立；未开启时明确记录为 disabled，不产生伪写入；
- 只在单实例进程中运行写入，不增加多 worker 或跨进程锁设计；采集与日报流水线共用进程内发布写锁；
- 每个任务级 commit 前必须由主审核 AI 审查完整 diff；未经用户批准不得推送、合并、部署或打 tag。

## 9. 验收标准

1. 空数据库可从迁移创建全部发布表和约束。
2. 同一 `canonical_key` 重复写入不会重复创建文章，并遵循发布时间、采集时间、来源摘要的更新优先级。
3. `articles`、`digests`、`digest_items`、GitHub 推荐、`sources` 和 `source_feeds` 满足网站设计字段及外键边界。
4. 仅经过基础治理且允许公开的候选会写入文章库；原始候选不会通过发布器进入公开库。
5. 日报、日报项和 GitHub 推荐任一写入失败时整体回滚；消息投递失败不删除已经发布的网站内容。
6. 发布库失败不把消息渠道写成成功，也不破坏 JSON 投递恢复与运行审计。
7. 来源展示名、稳定来源名、默认分类和 feed 地址分离；最终文章分类不被来源默认分类覆盖。
8. 全部新增行为具备正常、边界、降级和失败测试。

## 11. 交付前自检

- 已复核本计划、网站平台设计、内容治理和现有流水线；
- 仅修改本计划列出的范围，未改变选材和消息语义；
- 启用、未启用、写入失败和消息失败路径均有证据；
- 没有硬编码数据库 URL、密钥、机器路径或静默 fallback；
- 文档、示例配置、迁移和测试同步；
- 已检查完整 diff、敏感信息和未预期文件；
- 未验证的 PostgreSQL/部署步骤明确列出。

## 12. 交付格式

每次任务交付按仓库固定格式说明完成内容、实际修改文件、设计契约对应、检查命令、测试、未完成项、风险、设计冲突、范围外改动和主审核重点。版本完成前不修改 `pyproject.toml` 的正式版本号、不更新 `CHANGELOG.md`、不创建 tag。
