## 1. 背景

单端点测试不能证明三条公共 API 的字段边界、时区、清理和无副作用语义在组合情况下仍保持一致。版本退出前需要一组跨模块契约回归和明确的验收记录。

## 2. 目标

完成 v1.1.0 的 SQLite 端到端契约回归、完整质量检查和文档状态核对，为 v1.2.0 前端提供可依赖的公共 API 基线。

## 3. 前置依赖

- T1-T4 已完成，且每项任务的精确测试与主审核通过；
- 三条端点、调度清理和统一错误响应已定型；
- 发布库测试可使用 SQLite，生产 PostgreSQL 验证不在本任务中伪造。

## 4. 输入与输出契约

输入：带有公开、隐藏、过期、窗口边界、日报和多来源数据的隔离 SQLite 发布库；FastAPI 测试客户端；不启用真实采集与调度副作用的测试夹具。

输出：

- 三条端点的成功、空结果、参数错误、资源不存在和发布库不可用响应证据；
- 对字段白名单、状态过滤、稳定排序、分页、来源列表和清理状态序列的回归结果；
- 文档中的 T1-T5 状态、实际检查命令和未验证事项与代码事实一致。

## 5. 修改范围

1. 增加或完善跨端点 API 契约和集成测试。
2. 为公共请求无副作用、数据库失败脱敏、清理两次运行和字段反向泄露增加回归测试。
3. 同步 v1.1.0 计划和文档入口中的完成状态、检查记录及未验证项。

## 6. 禁止事项

- 不为通过测试修改已批准的接口、默认值、状态码或字段契约；
- 不顺手新增前端、认证、订阅、管理或部署能力；
- 不将 SQLite 成功描述为 PostgreSQL 或生产部署验证；
- 不修改正式版本号、变更记录或 tag。

## 7. 执行要求

- 先为发现的契约缺口写失败回归测试，再修复对应实现；
- 每项字段隔离测试同时覆盖泄露样本和相邻合法公开字段；
- 清理测试必须记录两次运行中状态、关联数和文章数的变化；
- 所有端点均验证请求前后发布库及 JSON 审计未被查询写入；
- 未能在真实 PostgreSQL 验证的内容登记唯一待办、前置条件和关闭标准，不得标记完成。

## 8. 实施步骤

1. 汇总 T1-T4 的契约测试矩阵并补齐缺口。
2. 执行 SQLite FastAPI 集成回归与清理状态序列测试。
3. 执行完整测试、lint、格式和公开边界检查。
4. 核对文档状态、完整 diff 和未验证项，提交版本级主审核。

## 9. 验收标准

1. 三条公共 API 在真实发布库测试数据上符合版本总览的响应契约。
2. 非公开内容和内部字段在组合查询、错误和空结果中均不泄露。
3. 日期、分页、排序和来源筛选在边界输入及两页以上数据下稳定。
4. 清理顺序与两次运行计数均得到验证，查询始终无副作用。
5. `make test`、`make lint`、格式检查和 `make check-public` 全部通过；未验证项明确登记。

## 10. 检查命令

```bash
./venv/bin/pytest tests/test_public_api.py tests/test_publication_store.py tests/test_app_api.py tests/test_ingest_job.py -v
make test
make lint
./venv/bin/ruff format --check .
make check-public
```

## 11. 交付前自检

- 已逐条映射版本退出条件和测试证据；
- 已运行精确与完整检查，结果未被模板或跳过测试伪造；
- 已检查完整 diff、文档状态、敏感信息和范围外改动；
- 已单列未验证的 PostgreSQL/部署验证及其关闭条件。

## 12. 交付格式

按仓库固定交付格式交付；主审核重点为跨端点字段隔离、清理状态序列、查询无副作用、未验证项登记和版本退出条件证据。
