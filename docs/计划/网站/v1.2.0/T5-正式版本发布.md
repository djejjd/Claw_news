## 1. 背景

T1-T4 只能完成公共前端功能验收。仓库规定正式版本必须由单独发布任务同步唯一版本来源、变更记录和可追溯文档，且 tag、推送、合并和部署均需用户明确授权。

## 2. 目标

在功能验收和主审核通过后，将正式项目版本同步为 `v1.2.0`，记录本版本公共网站能力及验证证据，并准备用户授权后的集成与 tag。

## 3. 前置依赖

- T4 已为 `completed` 且主审核结论为 `approved`；
- 完整 Python 与前端质量检查、公共边界检查和隔离真实路由 E2E 均有可追溯结果；
- 用户已确认版本退出条件满足。

## 4. 输入与输出契约

输入为 T1-T4 的完成记录和 `pyproject.toml` 当前 `1.1.0`。输出为 `pyproject.toml`、`CHANGELOG.md` 与版本计划一致的 `1.2.0` 发布准备状态；不创建 tag、不推送、不合并、不部署，除非用户在该时点另行明确授权。

## 5. 修改范围与接口变更表

| 变更 | 输入/返回 | 副作用 | 兼容性 | 测试 |
|---|---|---|---|---|
| 正式版本同步 | `1.1.0` -> `1.2.0` | 修改版本元数据 | 不改运行接口 | 版本一致性检查 |
| 变更记录与文档入口 | 已验收功能 -> 中文记录 | 仅文档 | 保留历史条目 | 链接与状态检查 |
| 保持应用行为 | 所有 API 和前端功能 | 无 | 不新增实现 | 完整回归 |

## 6. 禁止事项

- 不修改前端或后端实现、测试、API、数据库或部署；
- 未获用户明确授权不得创建 tag、push、merge、Release 或部署；
- 不将未验证项目描述为已完成。

## 7. 执行要求

版本号、CHANGELOG、计划状态和文档入口必须一致。提交前运行任务提交门禁和完整质量检查；主审核只审核发布范围。任何缺失验收证据都必须回到对应实现任务，不得通过修改版本记录掩盖。

## 8. 实施步骤

1. 核对 T1-T4 关闭记录、完整 diff 和全部验收证据。
2. 先写版本一致性检查或更新既有检查的预期失败断言。
3. 同步 `pyproject.toml`、`CHANGELOG.md`、文档入口和版本方案状态。
4. 运行完整质量检查、主审核和任务提交门禁。
5. 等待用户单独批准合并、推送、tag 或部署。

## 9. 验收标准

1. `pyproject.toml`、`CHANGELOG.md` 和文档记录均为 `v1.2.0`，且只描述已验收公共网站功能。
2. T1-T4 均已关闭并有批准记录，未验证项有唯一待办与关闭条件。
3. Python、前端、浏览器 E2E 和公开边界检查通过。
4. 未经用户明确授权，没有 tag、push、merge、Release 或部署。

## 10. 检查命令

`make test`；`make lint`；`./venv/bin/ruff format --check .`；`make check-public`；`make frontend-check`；`make frontend-e2e`；版本一致性检查；`make task-commit-check TASK=docs/计划/网站/v1.2.0/T5-正式版本发布.md`。

## 11. 交付前自检

确认只修改允许路径；版本三处一致；所有 T1-T4 验收有证据；无实现或部署改动；未验证项明确；用户外部操作授权状态已记录；主审核已检查完整 diff。

## 12. 交付格式

按仓库固定交付格式列出完成内容、文件、契约对应、检查结果、测试、未完成项、风险、冲突、范围外改动和主审核重点。
