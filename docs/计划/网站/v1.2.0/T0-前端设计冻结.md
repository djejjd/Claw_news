## 1. 背景

`v1.2.0` 的公共 API 已完成，但前端路由、页面状态、URL 语义、响应式和隔离 E2E 尚未作为用户批准的稳定设计冻结。没有可追溯设计基线，T1-T5 不能启用。

## 2. 目标

依据用户确认，将《公共网站前端设计》从 `pending_approval` 冻结为 `approved`，使版本方案、任务包、测试策略和文档入口一致，并创建可作为后续任务设计基线的设计提交。

## 3. 前置依赖

- `v1.1.0` 公共 API 设计已批准；
- 用户已确认启动公共网站前端设计；
- 本任务不包含前端、后端或测试实现。

## 4. 输入与输出契约

输入是用户已确认的设计范围和已批准公共 API。输出是明确记录批准角色、日期、待决问题为空及后续冻结 SHA 的中文前端设计；`/`、`/articles`、URL 参数、展示字段、错误状态、工具链、CI、隔离真实路由 E2E 和非目标必须同版本方案、T1-T5 一致。

## 5. 修改范围与接口变更表

| 变更 | 输入/返回 | 副作用 | 兼容性 | 验证 |
|---|---|---|---|---|
| 冻结前端设计 | 用户确认 -> `approved` 设计记录 | 仅文档 | 不改公共 API | 批准表、SHA、待决项检查 |
| 对齐版本方案与任务包 | 冻结设计 -> 任务引用与基线 | 仅文档 | 不改实现 | 任务解析、依赖与路径检查 |
| 更新文档入口 | 方案 -> 可发现链接 | 仅文档 | 保留既有链接 | Markdown 链接检查 |
| 保持运行行为 | 全部 API、调度与发布行为 | 无 | 完全保持 | diff 范围检查 |

## 6. 禁止事项

- 不创建 `frontend/`、不安装 Node 依赖、不修改 CI、Makefile 或任何应用代码；
- 不修改公共 API、数据库、采集、选材、摘要、投递、认证、部署或正式版本号；
- 不把待验证 E2E 或生产部署描述为已完成；
- 不在未提交设计基线前启用 T1-T5。

## 7. 执行要求

本任务为纯文档冻结，代码测试先行不适用。必须由独立启动审查确认用户授权、公共 API 基线、任务边界和 worktree；每次文档提交前均由独立主审核检查完整 diff。设计冻结需按以下顺序分为两个均属于 T0 允许范围的实现提交：第一提交记录 `approved` 设计；第二提交引用第一提交 SHA，回填设计批准表和 T1-T5 的设计基线。第二提交后才创建只修改 T0 与版本方案的关闭记录，之后才能启动 T1。

## 8. 实施步骤

1. 核对用户确认、公共 API 基线和当前 worktree。
2. 独立启动审查批准后，运行 T0 门禁。
3. 将前端设计的批准记录、版本方案和任务引用调整为一致状态。
4. 执行 Markdown、任务解析和 diff 范围检查。
5. 更新为 `review_pending`，经独立主审核批准后创建第一份设计冻结提交，任务仍保持 `review_pending`。
6. 以第一提交 SHA 更新设计批准表、版本方案和 T1-T5 的设计基线；再次取得独立主审核批准后创建第二份基线传播提交。
7. 仅以关闭记录记录第二份实现提交；关闭记录不得混入设计或后续任务包改动。

## 9. 验收标准

1. 前端设计具有 `approved` 状态、用户批准记录、无待决问题和可追溯的第一份设计冻结提交 SHA。
2. 所有 T1-T5 均引用该设计，且没有公共 API、实现或部署范围外变更。
3. 版本方案包含 T0，并在 T0 完成前阻止 T1 启用。
4. 文档入口可定位当前 `v1.2.0` 方案。
