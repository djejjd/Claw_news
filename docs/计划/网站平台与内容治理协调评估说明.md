## 1. 说明目的

本文用于评估《内容治理方案》是否要求整改《网站平台设计》及网站实施顺序。本文只整理影响、冲突和候选整改方向，不代表相关修改已经批准，也不替代后续实施任务包。

请审核方以《内容治理方案》的已定决策、现有稳定架构文档和代码契约为依据，逐项判断：

1. 是否需要整改；
2. 应修改哪一份设计或计划文档；
3. 应在网站开发前、治理 Phase 1 后或后续阶段处理；
4. 是否存在遗漏、过度设计或无法兼容的契约；
5. 是否需要先由用户补充决策。

## 2. 当前结论摘要

内容治理不会推翻网站的总体产品方向和技术选型，但会直接影响网站第一阶段的内容模型、来源模型、API 字段、管理后台观测能力和实施顺序。

> 审核结论（2026-08-14）：**需要整改**。已按裁决 1A（公共流过滤后准入）、2A（LLM 淘汰补位到 10 条、不重复调 LLM、不足正常降级）、3A（快讯源硬上限 2 / 其余源软上限 3 + 降级证据）完成文档整改：`内容治理方案.md` 补补位机制与上限语义，`网站平台设计.md` 修订内容/来源/日报模型与兼容原则，`路线图.md` 增加依赖顺序。

可以继续保持的设计包括：

- “公共新闻网站 + 私有运营后台”的产品方向；
- Vue 3 + TypeScript、FastAPI 和 PostgreSQL 技术选型；
- 服务端 Session、邀请制账户、CSRF 和角色校验；
- 公共日报与个人来源订阅相互独立；
- 最近 10 天内容保留策略；
- 单实例部署、网站发布与消息投递故障隔离。

需要在 PostgreSQL 内容发布库落地前重新核对的部分包括：

- 四分类运行时契约；
- 来源默认分类与文章最终分类的边界；
- 主题、相关性和治理证据是否进入发布模型；
- feed 级健康状态和失败原因如何持久化；
- 公共新闻流在流水线中的准入位置；
- LLM 相关性淘汰后的补位和发布事务语义。

## 3. 已确认的影响

### 3.1 分类从三类扩展为四类

《内容治理方案》已确定运行时分类为 `ai / tool / game / digital`，并将兼容别名 `device` 从 `tool` 调整到 `digital`。现有代码仍只接受 `ai / tool / game`，网站设计中的 `articles.category` 和来源分类若直接按现状建库，会固化旧契约。

候选整改方向：

- 数据库和 API 从第一版开始接受 `digital`；
- `device` 只作为输入兼容别名，不作为新的公开分类值；
- 分类枚举、校验、序列化、筛选和前端展示共用同一契约；
- 明确存量 `device` 数据的迁移规则和回滚方式。

### 3.2 来源分类不再等同于文章分类

网站设计目前把分类作为 `sources` 的属性；治理方案要求综合来源保留默认分类作为兜底，并在候选入池后根据具体内容动态重判。一个来源可以产生多个最终分类，因此来源分类不能继续被解释为文章的权威分类。

候选整改方向：

- 将来源或 feed 上的分类定义为 `default_category`；
- 将 `articles.category` 定义为内容级最终分类；
- 视审计需要保存分类来源、置信度和分类器版本；
- 管理后台修改来源默认分类时，不静默改写已经发布文章的最终分类。

### 3.3 主题和相关性成为发布契约的一部分

治理方案要求扩展全部类别的主题分类，并让 LLM 摘要输出 `relevance` 分作为兜底。网站日报需要展示或审计 LLM 结果，但当前 `digest_items` 只明确了核心摘要、重要性和趋势。

候选整改方向：

- 评估 `articles` 是否保存 `topic`、`topic_confidence`；
- 评估 `digest_items` 是否保存 `relevance`、LLM 判定版本和必要的淘汰证据；
- 公共 API 只返回用户需要的发布字段，详细规则命中和内部拒绝原因仅供管理接口使用；
- 不把内部 `CandidateItem` 直接序列化为公共响应。

### 3.4 来源健康需要下沉到 feed 维度

治理方案要求连续失败来源显示为 `degraded`，并按 feed 持久化失败原因。网站管理后台计划提供来源测试、运行状态和健康接口，因此 `source_feeds` 不能只有模糊的“最近状态”。

候选整改方向：

- 明确最近成功时间、最近失败时间、连续失败次数和最近错误摘要；
- 区分 source 聚合健康与单个 feed 健康；
- 保留完整内部错误与对外可展示状态之间的权限边界；
- 避免将瞬时失败直接永久写成来源停用。

### 3.5 来源扩展会影响订阅和默认集合

治理方案计划分批接入多个新来源。网站允许用户按来源订阅，且新增来源默认不加入已有用户，因此来源接入不仅是采集配置变更，也会影响来源种子、公开来源列表和新用户默认订阅集合。

候选整改方向：

- `SourceRegistryAdapter` 在网站内容库之前落地；
- 来源稳定标识不能依赖可变展示名或 feed URL；
- source 与 source_feed 保持一对多边界；
- 新来源上线、停用和默认订阅变更应具备显式审计语义。

### 3.6 运营闭环会影响管理后台范围

治理 L4 要求每日回放、来源和分类分布报表以及超标告警。网站第一版管理端已经包含运行状态，但尚未明确是否承担治理报表。

候选整改方向：

- 由审核方判断第一版只提供原始运行状态，还是同时纳入来源占比、分类分布和拒绝分布；
- 如果不纳入第一版，应将报表明确列为后续阶段，避免管理端范围被隐式扩大；
- 报表读取持久化指标，不在页面查询时触发回放或重新选材。

## 4. 需要优先裁决的契约问题

### 4.1 公共新闻流的准入位置

网站设计写明新闻流展示“当天全部成功采集、去重后的新闻”；治理方案又要求分类与相关性过滤。需要明确网站公开的是：

- 仅完成采集和 URL 去重的全部候选；或
- 已通过基础分类与规则相关性过滤的候选；或
- 经过完整选材但未进入日报的内容。

建议评估方向：公共发布库只接收完成基础规范化、去重、分类和规则相关性过滤且允许公开的内容；未经治理的原始候选仍保留在内部候选池。该建议需要审核确认，不能直接视为已定决策。

### 4.2 LLM 淘汰后的补位机制

治理方案采用“在现有摘要调用中输出 `relevance`，低于阈值淘汰”，但 LLM 调用发生在选出目标 10 条之后。当前文档没有定义淘汰后是否补位、补位是否再次调用 LLM、最多重试几轮，以及最终不足 10 条时如何标记状态。

审核方需要明确：

- LLM 相关性是仅标记、阻止发布，还是触发候选补位；
- 补位是否必须保持分类配额和单源上限；
- 日报不足 10 条是正常降级还是发布失败；
- 网站数据库事务应保存初选结果、最终结果还是两者的审计关系。

### 4.3 单源上限是硬约束还是软目标

治理方案一方面确定快讯源最多 2 条、其他来源最多 3 条，另一方面在风险章节称上限为“软目标”，候选不足时允许降级填充。两种语义会导致不同的选材、审计和验收结果。

审核方需要明确：

- 哪些来源上限绝不能突破；
- 是否只允许在总候选不足时突破；
- 突破上限是否必须产生显式降级状态和证据；
- 连续 7 天单源占比红线与单次降级突破如何共同验收。

### 4.4 “保持现有规则兼容”的准确含义

网站设计要求保持现有选材规则和 LLM 摘要输入兼容，但治理方案明确要修改分类、配额、评分、摘要输入长度和 LLM 输出结构。两者按字面无法同时成立。

候选整改方向：将兼容原则改成“保持采集、选材、摘要和投递之间的流水线接口可演进兼容；选材语义按已批准治理版本迁移”，并为字段和策略变化提供版本或迁移测试。

## 5. 建议的实施顺序

建议审核以下顺序是否合理：

1. 完成治理 Phase 1，建立来源上限、摘要截断、TapTap 修复和 feed 级健康基线；
2. 裁决本文第 4 节的四项契约问题；
3. 修订网站平台设计中的内容、来源、日报和健康数据模型；
4. 建立 PostgreSQL 内容发布基础和 `SourceRegistryAdapter`；
5. 完成治理 Phase 2 的四分类、动态分类和全类别主题分类；
6. 在稳定发布契约上实现公共 API 和 Vue 用户端；
7. 实现账户、来源管理和运行状态后台；
8. 将治理 Phase 3 和 L4 报表按批准范围接入管理后台。

该顺序不要求网站等待全部治理完成，但要求网站内容库不要先于关键分类和准入契约定型。

## 6. 建议整改范围

若审核结论为需要整改，建议优先评估以下文档，不直接扩大到代码实施：

- `docs/架构/网站平台设计.md`：修订内容模型、来源模型、发布准入和兼容原则；
- `docs/计划/路线图.md`：协调治理阶段与网站阶段的依赖顺序；
- `docs/架构/内容选材.md`：治理实现完成后同步四分类、上限和补位语义；
- `docs/架构/来源管理.md`：治理实现完成后同步默认分类、动态分类和 feed 健康；
- `docs/产品/产品说明.md`：治理实现完成后同步用户可见分类与来源上限。

不得在评估整改时直接实现 PostgreSQL、API、前端或治理算法；代码实施应另建符合仓库十二段要求的任务包，并遵循测试先行。

## 7. 审核方交付要求

请按以下结构输出评估结果：

1. 总体结论：需要整改、部分整改或无需整改；
2. 逐项判断：对应本文第 3、4、5 节逐项给出结论和理由；
3. 必须整改项：列出文档、章节和建议文本方向；
4. 可延后项：说明延后到哪个阶段及其前置依赖；
5. 不采纳项：说明为何属于过度设计或超出第一版范围；
6. 需要用户裁决的问题：只列无法由现有批准设计推导的问题；
7. 设计冲突：列出治理方案、网站设计和现有代码之间无法兼容之处；
8. 建议整改顺序：给出依赖关系，不直接实施；
9. 风险：说明不整改可能造成的数据迁移、API 兼容或运营风险；
10. 范围声明：确认评估没有擅自扩大到代码开发、提交、推送或部署。
